The URL alone is not enough to fetch encrypted bytes.

New share links keep the filename and content type inside the same password boundary as the file. The browser derives a proof from the password, and the backend verifies it before releasing the encrypted payload.

  • Source checks on every requestThe share is available only while its source remains active and the owner still has the required access.
  • Finite request budgetNew links default to ten encrypted-payload requests, with an owner-selected limit from 1 to 1,000.

A revoked link cannot pull back a downloaded copy.

Encryption and link controls narrow access before and during a transfer. They cannot control a file after an authorized recipient has decrypted and saved it elsewhere.

Treat the full share link, file-request link, and password as sensitive. Confirm the recipient, use separate channels for the link and password when practical, and revoke access that is no longer needed.

Support safety: Never send support a complete secret-bearing link, password, recovery material, private key, or authentication code.

Encrypted file sharing FAQ

How does a password-protected RonikCloud share work?

RonikCloud creates a separate encrypted share copy. The recipient's browser derives a proof from the password, the backend checks it before encrypted bytes leave storage, and the browser decrypts the protected file.

Can a share link be limited or revoked?

Yes. New links have an expiry and encrypted-payload request budget, and the owner can revoke a link. Revocation cannot recall a copy that a recipient already downloaded.

What does a recipient need to decrypt a shared file?

The recipient needs the complete share link and its password. After the backend accepts the password proof, the browser downloads and decrypts the protected share copy.
