Collect the source material without inviting someone inside.

A file request fits the moment when another person needs to send something sensitive, but does not need your folder tree, workspace history, or member permissions.

  • Professional documentsRequest signed agreements, project briefs, reports, or other source documents through one focused handoff.
  • Creative source filesCollect photographs, design assets, audio, or exported project files without turning the sender into a workspace member.

  • Follow-up materialsOpen a separate bounded request when a client needs to supply another revision or missing input.

A small upload page with explicit limits.

The public page is intentionally narrower than the owner's workspace. It uses a limited metadata endpoint and does not read the private request document directly.

01

A protected request title

The browser opens the encrypted title with the key from the private fragment. The public metadata response does not reveal the owner account.

02

Visible collection boundaries

The page shows the maximum file size, remaining submission slots, and an approximate availability time derived from the coarse request expiry.

03

Fixed recovery guidance

Invalid keys, closed requests, upload limits, and interrupted transfers use bounded guidance. Provider response bodies are not displayed to the contributor.

The private fragment protects content, not every trace of activity.

Encryption narrows what storage and the public page receive in readable form. It does not make the account relationship, request limits, network connection, or service operation disappear.

RonikCloud still processes the owner relationship, opaque request, upload, and object identifiers, coarse expiry, file-size and upload limits, counts, status, encrypted payload sizes, storage routing, and limited security records. Service infrastructure can observe connection data, timing, and traffic volume.

Encrypted file request FAQ

Does a contributor need access to my RonikCloud workspace?

No workspace access is needed. The contributor opens a focused public file-request page with the complete private link, chooses a file, and submits it from the browser. Anyone holding that complete link can use the request while it remains active, so send it through a trusted channel.

What does an encrypted file request protect?

The owner encrypts the request title before creating the link. The contributor's browser encrypts the submitted filename, content type, and file body before upload. The private encryption key is carried in the URL fragment, which browsers do not send with the HTTP request, and in a separate owner-encrypted envelope.

How can I limit or close a file request?

A request has an expiry, a maximum file size, and a completed-upload limit. The owner can close it earlier. A temporarily reserved upload slot is released automatically after an abandoned attempt, so that temporary state is different from reaching the completed-upload limit.

Does encryption hide every detail about a requested upload?

No. RonikCloud still processes the owner relationship, opaque request, upload, and object identifiers, expiry, file-size and upload limits, counts, status, encrypted payload sizes, storage routing, and limited security records. Service infrastructure can also observe connection data, timing, and traffic volume.
